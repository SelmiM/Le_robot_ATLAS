# Robot interfaces

| Interface      | Defined in                                                | Used by                                 |
| -------------- | --------------------------------------------------------- | --------------------------------------- |
| JSON protocol  | `Robot::execute()` (commands), `Robot::send*()` (replies) | Any client, over USB serial or HTTP     |
| `Robot.h` API  | `robot/Robot.h` and the device headers                    | Firmware missions and commands          |
| `robot.js` API | `robot/web/robot.js`                                      | The phone page, `robot/web/missions.js` |

Only JSON lines cross the link. `robot.js` and `Robot.h` are programming interfaces on either end and share no code. A forward movement from the phone:

```
robot.js API                    JSON protocol            Robot.h API
phone, JavaScript               over HTTP                robot, C++
─────────────────               ─────────────            ───────────
seq = bot.forward(200, 1000) ─► POST /api/command     ─► execute()
                                {"seq":8,"left":200,       drive(200, 200, 1000)
                                 "right":200,
                                 "duration":1000}

bot.last                     ◄─ GET /api/lines        ◄─ sendTelemetry()
  polled every 100 ms           {"seq":8,"ms":41230,       every 200 ms
                                 "moving":true,…}

await bot.waitUntilDone(seq) ◄─ GET /api/lines        ◄─ enforceSafety()
                                {"seq":8,"ms":42230,       after 1000 ms
                                 "moving":false,…,
                                 "done":true}
```

A firmware mission never crosses the link: `mission()` calls `drive()` on the robot itself. [`README.md` — Firmware and phone missions](README.md#firmware-and-phone-missions) compares the two.

## JSON protocol

The HTTP routes are listed in [`README.md` — HTTP interface](README.md#http-interface).

### Commands

Each command is a flat JSON object. Over USB serial, send one object per line; `POST /api/command` accepts the same lines in its request body. Fields can be combined in one command. Use integers for speeds, times, mission numbers and tags; `stop` and `info` are booleans. `null` acts like an omitted field; fractional numbers, arrays and nested objects are rejected.

| Command                                     | Effect                                           |
| ------------------------------------------- | ------------------------------------------------ |
| `{"left":200,"right":200}`                  | Both sides forward for the default one second    |
| `{"left":200,"right":-200,"duration":3000}` | Spin for three seconds                           |
| `{"stop":true}`                             | Stop the wheels now and cancel the robot mission |
| `{"telemetry":500}` / `{"telemetry":0}`     | Report every 500 ms / disable periodic telemetry |
| `{"mission":1}` / `{"mission":0}`           | Select mission 1 / turn the robot mission off    |
| `{"info":true}`                             | Send a separate robot-information line           |
| `{"seq":7,"left":100,"right":100}`          | Store tag 7 for subsequent telemetry             |

`left` and `right` are signed speed settings, clamped to -255 (reverse) through +255 (forward); zero stops that side. If either wheel is specified, an omitted wheel is set to zero. A movement replaces the previous movement and arms a new deadline: `duration` is in milliseconds, defaults to 1000 when absent or negative, and is capped at 5000. A zero duration expires immediately. A settings-only command (for example `{"telemetry":500}` or `{"mission":0}`) does not change the wheel speeds or deadline. `stop:true` takes precedence over wheel fields in the same object.

The starter firmware defines no numbered missions yet; their behavior is added in `Robot::mission()`. Selecting a mission changes the mission number reported below. `telemetry` defaults to 200 ms; zero or a negative value disables only **periodic** reports.

### Command tags (`seq`)

`seq` is an optional integer supplied by the sender, not a counter generated by the robot. It starts at `-1` on boot. Each command that supplies it replaces the stored value, even a settings-only or stop command; an untagged command leaves the old value in place. **Every subsequent telemetry line carries the latest stored `seq`**, including periodic lines after the movement has ended. It is therefore not a unique movement ID or a separate reply to each command. For example, if `{"seq":7,"left":200,"right":200}` is followed by `{"seq":8,"telemetry":100}`, the completion line for the movement can have `"seq":8`. An untagged command would leave it at 7 instead.

Telemetry is normally sent on the periodic schedule, not immediately in response to a command. With periodic reports off, there may be no telemetry acknowledging a settings-only command. HTTP's `after=N` and `X-Last-Line` number **outgoing lines** independently of `seq`; a successful command POST returns `204 No Content`, not a JSON acknowledgment.

### Lines sent by the robot

Each outgoing message is one JSON object on one line. For example, after `{"seq":7,"left":200,"right":200,"duration":1000}`, these are three illustrative telemetry lines (while moving, at the deadline, and later):

```json
{"seq":7,"ms":41230,"left":200,"right":200,"moving":true,"mission":0,"front_mm":412,"front_ok":true,"front_q":-1,"side_mm":-1,"side_ok":false,"side_q":-1}
{"seq":7,"ms":42230,"left":0,"right":0,"moving":false,"mission":0,"front_mm":412,"front_ok":true,"front_q":-1,"side_mm":-1,"side_ok":false,"side_q":-1,"done":true}
{"seq":7,"ms":42430,"left":0,"right":0,"moving":false,"mission":0,"front_mm":412,"front_ok":true,"front_q":-1,"side_mm":-1,"side_ok":false,"side_q":-1}
```

| Field                 | Meaning                                                                                                                                                           |
| --------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `seq`                 | Latest command tag, or `-1` if none has been supplied                                                                                                             |
| `ms`                  | Milliseconds since robot boot                                                                                                                                     |
| `left`, `right`       | Current requested wheel speeds, not measured motion                                                                                                               |
| `moving`              | `true` if either wheel's requested speed is nonzero                                                                                                               |
| `mission`             | Selected robot mission number; `0` means none                                                                                                                     |
| `front_mm`, `side_mm` | Last distance in millimetres, or `-1` when unavailable                                                                                                            |
| `front_ok`, `side_ok` | Whether that sensor's last reading is valid; check before using its distance                                                                                      |
| `front_q`, `side_q`   | Signal quality: front is always `-1` (ultrasonic has no signal rate); side is the VL53L1X signal rate in thousands of counts per second, or `-1` when unavailable |
| `done`                | Present as `true` only when the safety check stops moving wheels; absent on other telemetry lines                                                                 |

Sensor validity describes the **last reading**, not how recently it was taken. The side sensor is disabled by default, which explains its `-1` / `false` values in the examples. An invalid side reading may still have a signal-quality value; check `side_ok` before using `side_mm`.

The robot emits a `done:true` line when moving wheels stop at their deadline or on link loss (which also cancels the robot mission). This line is sent even when periodic telemetry is disabled. It may not reach a client whose link was lost. An explicit `{"stop":true}` (or a command setting both wheel speeds to zero) stops immediately **without** a `done` line; replacing one movement with another also does not complete the old movement separately. A `done:true` line does not prove that the command shown in `seq` ran for its full requested duration.

Other outgoing JSON lines are not telemetry and have no `seq`:

```json
{"info":true,"robot":"robot","missions":"","camera":false}
{"error":"that was not valid JSON"}
```

`{"info":true}` requests a line with the configured robot name, comma-separated mission names (empty in the starter firmware), and whether the camera is connected. An `error` line reports a rejected malformed command. Both can appear among the numbered lines returned by `GET /api/lines`.

## Robot.h API

### Main loop

`Robot::update()` runs on every pass through the main loop, in this order: sensor updates, `readCommands()`, `mission()`, `enforceSafety()`, telemetry, display. Nothing called from it may wait: a blocked pass also delays the deadline and link checks.

### Movement

```cpp
void drive(int left, int right, uint32_t durationMs = DEFAULT_DURATION_MS);
```

Sets both wheel speeds, from -255 (reverse) to +255 (forward), and arms a deadline. Speeds outside that range are clamped; zero stops that side. `durationMs` is capped at `MAX_DURATION_MS`. Each call replaces the previous movement and its deadline; to keep moving, call `drive()` again before the deadline passes.

`enforceSafety()` stops the wheels when the deadline passes or the link is lost. `motors.stop()` stops them at once. Do not call `motors.set()` directly: `enforceSafety()` treats a movement without a deadline as a fault and stops it on the next pass.

### Missions

`_mission` holds the selected mission number. `{"mission":N}` sets it; `{"stop":true}` and a lost link reset it to 0. `mission()` runs on every pass and dispatches on it:

```cpp
static constexpr const char* MISSION_NAMES = "wiggle";

void mission() {
  switch (_mission) {
    case 0: break;
    case 1: wiggle(); break;
    default: break;
  }
}

// Turn left and right in turn, 400 ms each.
bool     _wiggleLeft = false;
uint32_t _wiggleAt   = 0;

void wiggle() {
  if (nowMs() - _wiggleAt < 400) return;   // not yet
  _wiggleAt   = nowMs();
  _wiggleLeft = !_wiggleLeft;
  drive(_wiggleLeft ? -150 : 150, _wiggleLeft ? 150 : -150, 400);
}
```

Keep each mission's state in members next to its method. A mission must return at once on every call, use `nowMs()` for time and `drive()` to move.

`MISSION_NAMES` lists the missions in number order, comma-separated. The robot reports it in its `info` line, and the phone page shows one button per name.

### Time

```cpp
uint32_t nowMs();   // Clock.h: milliseconds since boot
```

The counter wraps after about 49 days. Compare elapsed times by subtraction:

```cpp
if (nowMs() - startedAt > 1000)   // right: still works at the wrap
if (nowMs() > startedAt + 1000)   // wrong: breaks at the wrap
```

### Distance sensors

`front` is the ultrasonic ranger (`UltrasonicSensor.h`); `side` is the VL53L1X (`TofSensor.h`), disabled by default with `SIDE_SENSOR_ENABLED`. `Robot::update()` polls both at the start of each pass. The front sensor completes a reading about every 60 ms, the side sensor about every 40 ms.

| Method         | Returns                                                                                       |
| -------------- | --------------------------------------------------------------------------------------------- |
| `connected()`  | Whether the sensor has answered; false at startup can turn true later                         |
| `valid()`      | Whether the **last** reading succeeded: `connected()` and `status()` is `0`                   |
| `distanceMm()` | Last distance in millimetres; `-1` unless `valid()`                                           |
| `quality()`    | Front: always `-1`. Side: signal rate in thousands of counts per second                       |
| `status()`     | `0` for a good reading. Front: `1` no echo, `2` out of range. Side: see `drivers/VL53L1X.cpp` |

Check `valid()` before using `distanceMm()`:

```cpp
if (front.valid() && front.distanceMm() < 200) { ... }
```

### Motors

| Method              | Effect                                                       |
| ------------------- | ------------------------------------------------------------ |
| `left()`, `right()` | Requested speed of each side, -255..255; not measured motion |
| `isMoving()`        | `true` if either requested speed is nonzero                  |
| `stop()`            | Set both speeds to zero                                      |

### Display

| Method                      | Effect                                                         |
| --------------------------- | -------------------------------------------------------------- |
| `connected()`               | Whether the LCD answered at startup                            |
| `line(row, text)`           | Write row 0 or 1, padded to 16 columns; longer text is dropped |
| `alreadyShowing(row, text)` | `true` if that row already shows `text`                        |

A two-row write blocks the loop for about 3 ms. `refreshDisplayIfDue()` rewrites both rows every `DISPLAY_REFRESH_MS`; edit it to display other text.

### Camera

Set `CAMERA_ENABLED` in `Config.h`; the camera requires `RADIO_WIFI`.

| Method                | Effect                                                                |
| --------------------- | --------------------------------------------------------------------- |
| `connected()`         | Whether the camera answered at startup                                |
| `capture()`           | Take a picture, replacing the last one; blocks about 30 ms            |
| `hasPicture()`        | `true` after the first successful `capture()`                         |
| `pixel(x, y)`         | Grey level, 0 (black) to 255 (white); `-1` outside or with no picture |
| `brightness()`        | Average grey level; `-1` with no picture                              |
| `width()`, `height()` | 324 and 244                                                           |

`x` runs left to right and `y` top to bottom, from 0. Call `capture()` on demand, not on every pass.

### Adding a command

Handle it in `execute()`, which receives each parsed command as a `JsonReader`:

| Method                           | Returns                                        |
| -------------------------------- | ---------------------------------------------- |
| `has(key)`                       | Whether the field is present; `null` is absent |
| `integer(key, fallback = 0)`     | The field as a `long`, or `fallback`           |
| `boolean(key, fallback = false)` | The field as a `bool`, or `fallback`           |

Use `has()` to tell a missing field from zero. `execute()` must not wait. To send a reply line, follow `sendInfo()`: fill a `JsonWriter`, then pass its `finish()` to `_radio.send()`.

### Settings

| `Config.h`             | Default | Meaning                                                           |
| ---------------------- | ------- | ----------------------------------------------------------------- |
| `DEFAULT_DURATION_MS`  | 1000    | Movement duration when none is given                              |
| `MAX_DURATION_MS`      | 5000    | Cap on a `drive()` duration                                       |
| `DEFAULT_TELEMETRY_MS` | 200     | Telemetry period at startup                                       |
| `WEB_TIMEOUT_MS`       | 1500    | Under WiFi, time without a request before the link counts as lost |
| `DISPLAY_REFRESH_MS`   | 500     | Display refresh period                                            |

## robot.js API

`robot/web/robot.js` is the ES module used by the phone page. The robot serves it with the page; edits need a rebuild and reflash, except against `client/fakerobot.js`, which reads it from disk.

```js
import { Robot, Mission } from './robot.js';

const bot = new Robot();
bot.start();
const seq = bot.forward(200, 1500);
await bot.waitUntilDone(seq);
```

### Connection

| Member                            | Effect                                                                      |
| --------------------------------- | --------------------------------------------------------------------------- |
| `new Robot(base = '')`            | Client for the robot at `base`; `''` targets the robot that served the page |
| `start()`                         | Poll `GET /api/lines` every `POLL_MS` (100 ms)                              |
| `pause()`                         | Stop polling; the robot stops its wheels `WEB_TIMEOUT_MS` later             |
| `connected`                       | `true` if the robot answered within the last second                         |
| `on(listener)`, `off(listener)`   | Register or remove `listener(message)`, called for each received line       |
| `last`                            | The most recent telemetry line                                              |
| `info`                            | The most recent `info` line                                                 |
| `latency.request`, `latency.loop` | Delays in ms, each with `last`, `mean` and `max`                            |

`latency.request` is the HTTP round trip of a command; `latency.loop` is the time until the first telemetry line carrying its `seq`.

The client also passes listeners two messages of its own: `{error: ...}` when the robot answers a command with an HTTP error, or does not answer after three retries; `{restarted: true}` when the robot's line numbering goes backwards, meaning it rebooted and lost its settings.

### Command methods

Each method sends one command and returns its `seq` tag at once, without waiting for the robot.

| Method                                   | Sends                                                   |
| ---------------------------------------- | ------------------------------------------------------- |
| `send(command)`                          | `command`, tagged with the next `seq` unless it has one |
| `drive(left, right, duration = 1000)`    | `{left, right, duration}`                               |
| `forward(speed = 200, duration = 1000)`  | `drive(speed, speed, duration)`                         |
| `backward(speed = 200, duration = 1000)` | `drive(-speed, -speed, duration)`                       |
| `turnLeft(speed = 200, duration = 500)`  | `drive(-speed, speed, duration)`: on the spot           |
| `turnRight(speed = 200, duration = 500)` | `drive(speed, -speed, duration)`: on the spot           |
| `stop()`                                 | `{stop: true}`                                          |
| `mission(number)`                        | `{mission: number}`; 0 is off                           |
| `telemetry(periodMs)`                    | `{telemetry: periodMs}`; 0 is off                       |

Tags start at a random value, so telemetry left over from before a page reload does not match a new command.

### Waiting

```js
waitUntil(test, timeoutMs = 10000, aborted = null)
waitUntilDone(seq, timeoutMs = 6000, aborted = null)
```

`waitUntil()` resolves to the first message for which `test(message)` is true, or to `null` when `timeoutMs` runs out or `aborted()` returns true. Only messages arriving after the call count. `test` sees every message, including `info` and `error` lines.

`waitUntilDone(seq)` waits for a `done:true` line whose `seq` is at least `seq`, not equal to it: a later command, such as `telemetry()`, replaces the tag the robot reports. Prefer it to sleeping for the requested duration: the `done` line reports, in `ms`, when the robot stopped the wheels.

### Mission

`Mission` builds a sequence of steps. Each method returns the mission, so calls chain:

```js
new Mission('carre')
  .forward(180, 1000)
  .turnRight(180, 600)
  .repeat(4)
  .stopWhen((t) => t.front_ok && t.front_mm < 200, 'quelque chose devant');
```

| Method                                                  | Effect                                                            |
| ------------------------------------------------------- | ----------------------------------------------------------------- |
| `drive`, `forward`, `backward`, `turnLeft`, `turnRight` | Add a movement step; same arguments as `Robot`                    |
| `pause(duration = 500)`                                 | Add a step that stops the wheels for `duration` ms                |
| `repeat(times)`                                         | Repeat every step so far, `times` times in total                  |
| `stopWhen(test, reason)`                                | End the mission when `test(telemetry)` is true                    |
| `run(bot, { log, aborted })`                            | Execute the steps; resolves to `{ completed, stoppedAt, reason }` |

`run()` sets telemetry to 100 ms, sends each step and waits for its `done` line, up to the step's duration plus 2 s. It ends early when the `stopWhen` condition holds, when `aborted()` returns true or when a step gets no `done`. It always leaves the robot stopped. `log(text)` receives one line per step; it defaults to `console.log`. `stoppedAt` is the zero-based index of the step that did not complete.

`stopWhen()` tests the latest telemetry received by the phone, not a live sensor reading.

To add a phone mission, add an entry to `missions` in `robot/web/missions.js`: a function that takes the page's `{ speed, duration, distance }` settings and returns a `Mission`. The page also calls it without arguments to count the steps, so give every setting a default:

```js
avancer: ({ speed = 180, duration = 1000 } = {}) =>
  new Mission('avancer')
    .forward(speed, duration),
```
